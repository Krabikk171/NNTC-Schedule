# NNTC Schedule 3.1.1 — обновление приложения через GitHub

Эта ветка — **исходники для проверки**, а не опубликованный подписанный APK.

## Что сделано

- Проверка GitHub Releases каждые ~24 часа через отдельный WorkManager, не связанный с проверкой PDF каждые 30 минут.
- Раздел **Настройки → Обновление приложения** с каналами Stable/Beta и ручной проверкой.
- Раздельные уведомления о новых APK (если Android разрешил уведомления).
- Загрузка APK только по нажатию пользователя, контроль размера, SHA-256 GitHub-asset и Android-подписи.
- Установка только через системный установщик после согласия пользователя.
- Для APK без корректных метаданных `update.json`, SHA-256 или совпадающего сертификата обновление **не устанавливается**.

## Стабильный выпуск v3.1.1 (39)

Описание для GitHub: приложение получает обновления APK через GitHub с проверкой контрольной суммы, пакета, версии и сертификата. Улучшен разбор кабинетов вида «1 корпус, 409». В диагностике расписания отдельно видны ручная попытка, периодическая попытка и последняя успешная фоновая проверка. Уведомления показывают источник проверки.

1. После успешного CI открыть проверенный коммит в Android Studio. Build → Generate Signed Bundle / APK → APK → app → release. Использовать прежние хранилище и alias публичной 3.1.0. Сохранить в отдельную папку под именем NNTC-Schedule-v3.1.1.apk.
2. Проверить командой apksigner verify --verbose --print-certs действительность V2 и одного подписанта с SHA-256 5FA982263E8A27D2274E1C2B34B109BEC8B72C5DDAA7053E1269C13E6BF9448B. В aapt dump badging сверить ru.krabikk.nntcschedule, 3.1.1, 39 и отсутствие application-debuggable. Записать размер и Get-FileHash -Algorithm SHA256.
3. Из корня этой ревизии выполнить python tools/create_update_manifest.py --apk "<путь к APK>" --output "<папка выпуска>/update.json". Сверить четыре поля с APK и будущим тегом.
4. После разрешения владельца повторно проверить свободный тег v3.1.1. Выпуск должен указывать на проверенный коммит и содержать APK и update.json. Для Stable отключить pre-release и назначить выпуск Latest. После публикации сверить /releases/latest, отсутствие draft и prerelease, состояние uploaded, размер и digest файла.
5. На устройстве с dev.3 зафиксировать группу, настройки и офлайн-расписание. До скачивания проверить предложение 3.1.1 (39) сначала в Stable, затем в Beta. Выполнить обновление поверх 38. Первый запуск провести без сети и сверить данные. После восстановления связи повторить проверку в обоих каналах: версия 39 не должна предлагаться повторно.

По наблюдениям владельца dev.3 фоновая синхронизация прошла 23 ноября в 22:33 и 24 ноября в 01:31 при неизменных времени ручной попытки и ID задачи. Доставку уведомления при настоящем изменении расписания предстоит проверить на телефоне. Для подтверждения восстановления после перезагрузки нужно установить факт перезагрузки.

## Проверка dev.3 на основном телефоне

1. На dev.2 зафиксировать группу, настройки и доступное офлайн-расписание. После обновления поверх 37 запустить dev.3 без сети и сравнить сохранённые данные. Ранее сохранённая ошибка кабинета может быть видна до обработки PDF исправленным парсером.
2. После синхронизации PDF за 23–24 ноября открыть группу 2РПУ-25-1 за вторник 24 ноября. У пар 08:10–09:40 и 10:00–11:30 проверить «Информатика и вычислительная техника», «1 корпус, 409», «Булатова Т.М.». Если сервер уже сменил документ, использовать регрессионный тест с сохранёнными координатами.
3. Выбрать интервал 30 минут. Записать ID и состояние schedule_auto_update, время ручной попытки, периодической попытки и последнего фонового успеха. Закрыть приложение обычным способом, оставить сеть доступной. Через несколько интервалов снять показания до нажатия кнопки проверки. Для неизменного PDF ожидается фоновый успех без уведомления.
4. Перезагрузить телефон, разблокировать и оставить в сети. До ручной проверки сравнить ID, состояние и время фонового успеха с предыдущими. При задержке записать режим батареи и время наблюдения. WorkManager допускает сдвиг запуска.
5. При изменении выбранной группы сверить источник «Автопроверка расписания» и обновлённые занятия. Повторная ручная проверка неизменного PDF не должна дать повторное уведомление. После отключения автопроверки проверить отсутствие новых периодических попыток.



## Настройка на устройстве

Откройте **Настройки → Обновление приложения**, выберите Stable/Beta (Stable по умолчанию), нажмите «Проверить сейчас». При новой версии нажмите «Скачать обновление». После проверки SHA-256 и сертификата можно нажать «Установить через Android». На Android 8+ может понадобиться отдельно разрешить установку из этого источника и вернуться в приложение.

## Особенности и ограничения

- При установленной debug-сборке скачанный релизный APK будет отклонён: подписи должны совпадать.
- Переход на меньший/equal `versionCode` запрещён.
- При отсутствии сети проверки и скачивание можно повторить позже.
- Приложение не обладает правом незаметной установки обновлений.
- В старых версиях 3.1.0 встроенной проверки APK нет; запустить её из предыдущей версии невозможно.
- При выпуске в магазинах приложений `REQUEST_INSTALL_PACKAGES` необходимо отдельно сверить с политикой магазина. Эта реализация рассчитана на распространение APK напрямую через GitHub/Telegram.
- Проверка `app-release.apk` и подпись на ПК не делаются в этой среде: финальная проверка выполняется в Android Studio на Windows.

## Проверка проекта

`gradlew.bat :app:assembleDebug :app:testDebugUnitTest`

Проверить на Android 7, Android 8+ и Android 13+: разрешения, скачивание, отмену, повреждённый APK, переключение каналов, обновление поверх v3.1.0 **без потери данных**. Не удалять опубликованную v3.1.0 и не перезаписывать ключи подписи.
